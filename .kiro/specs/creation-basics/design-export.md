# 書き出し（空の土台と、色の変わった部品）

要件2.1〜2.5・4。第2段階の書き出し（[design-export.md](../editor-foundation/design-export.md)）の決まり「元のバイト列を土台にし、変えた所だけを直し、足す物は配列の末尾に足す。既存の要素の番号は1つも変えない」を保つ。

## 確かめた事実
- `export::build` は、ファイルにある部品について、位置・名前・子の並びだけを比べて書き換える。**描画（`ExportNode.draws`）は、足した図形の部品でしか読んでいない。** いま色を変えても、ファイルにある部品の色は書き出されない。
- 複製は、写す元のノードの JSON をそのまま写す（`mesh` の番号も同じ）。
- 足した図形は、`Appender` が色ごとに材質を1つ（基本色と `metallicFactor: 0`）、「形状と色の並び」ごとにメッシュを1つ作る。形状のアクセサは形状ごとに1回だけ足す。**足した図形の色は、今の仕組みのまま書き出される。**
- 読み込みは、点と線のプリミティブと、読めなかったプリミティブを描画にしない。**部品の i 番目の描画が、メッシュの i 番目のプリミティブとは限らない。**
- 土台を読む `export::base::read` は、読み込みと同じ組み立て（`build::assemble`）を呼ぶ。組み立ては、描画が1つも無いと `NoMesh` で失敗する。**空の GLB は、今のままでは土台にできない。**
- 照合（`export::verify`）は、「メッシュや材質を足したのに BIN を足していなければ失敗」「足した材質の `metallicFactor` が 0 でなければ失敗」「ファイルにあるノードの `mesh` が変わっていれば失敗」としている。色の写しは、この3つに当たる。

## 空の土台
```rust
// gltf::export（synth.rs に足す）
/// ノードもメッシュも無い最小の GLB。JSON チャンクだけで、BIN は無い。いつも同じバイト列を返す。
pub fn empty_base() -> Vec<u8>;
// app::exporter
pub enum ExportBase { File, Stl { unit: UnitLabel, name: String }, Empty }
```
- JSON は `{"asset":{"generator":"model-reviewer","version":"2.0"},"scene":0,"scenes":[{"nodes":[]}]}`。キーの並びは、今の書き出しと同じ直列化に任せる。
- `base::read` は、土台のノードが0個で、組み立てが `NoMesh` を返したときだけ、`Model::empty()` を土台のモデルにする（`build` の中に、土台用の入口を1つ足す。**`load_glb` は変えない**。メッシュの無いファイルを開く操作は、今までどおり断る）。
- 書き出しのスレッドは、`ExportBase::Empty` のとき、ファイルを読む工程と識別の照合を飛ばし、`empty_base()` を土台のバイト列にする。あとは今の `build`・`write_container`・照合である。
- `build` は、足りない配列（`nodes`・`meshes`・`materials`・`accessors`・`bufferViews`・`buffers`）を作って足す形になっている（`array_mut` と `buffers` の分岐を読んで確かめた）。シーンの根は「土台と違えば書き換える」分岐で入る。
- 描画を持つ部品が無い文書は、`Session` が先に断る（要件2.2）。`build` の側でも、土台が空で、足す描画が1つも無ければ `InvalidScene` を返す（照合が開き直せないファイルを書かない）。

## 色の変わった部品
`export/recolor.rs`（新規）に置く。`patch::build` から呼ぶ。
1. **どの描画がどのプリミティブかは、読み込みが作った対応をそのまま使う。** `build::assemble` の内部の結果に「描画ごとの（メッシュの番号、プリミティブの番号）」を足し、`Base` が持つ（公開しない）。書き出しの側で数え直さない（読み込みと食い違う余地を作らない）。
2. **変わったかどうかは、土台のモデルの色とビット単位で比べる。** ファイルにある部品は自分のノード、複製は写す元のノードの描画と比べる。描画の数が合わなければ `InvalidScene`。形状の番号は比べない（削除して書き出した後に取り消すと、文書の番号は最初のモデルの数え方のままで、読み直した土台とずれるため。形状の中身は照合が比べる。2026-11-27 の実装で決めた）。
3. **材質の写し。** 鍵は（元の材質の番号、新しい色のビット）。元の材質の JSON を写し、`pbrMetallicRoughness.baseColorFactor` だけを新しい色（4つの値。透明度は元のまま）にする。`pbrMetallicRoughness` が無ければ作る。元のプリミティブに材質が無ければ、`{"pbrMetallicRoughness":{"baseColorFactor":[…]}}` だけの材質を作る（ほかは既定のままで、元と同じ見え方を保つ）。
4. **メッシュの写し。** 鍵は（元のメッシュの番号、プリミティブごとの材質の番号の並び）。元のメッシュの JSON を写し、色の変わったプリミティブの `material` だけを替える。`attributes`・`indices`・`targets`・`weights`・`extras`・描画にならなかったプリミティブは、元のまま写る。
5. **ノード。** その部品のノードの `mesh` を、写したメッシュの番号にする。同じメッシュを使うほかのノードは、元の番号のままである。
6. **足さないもの。** アクセサ、バッファビュー、BIN。写したメッシュは、元と同じアクセサを指す（形状のデータは1バイトも増えない）。
7. 結果に `ExportNote::Recolored { nodes: u32, materials: u32, meshes: u32 }` を足す。
- 取り消して元の色に戻した部品は、2 で「変わっていない」になり、元のメッシュを指したままになる。
- 書き出して作業の対象が移った後は、新しいファイルが土台になる。色はその時点で土台と同じなので、次の書き出しで写しは増えない。**そのために、書いた色が読み直した色とビット単位で同じであることを照合で確かめる**（下）。
- 使われなくなった材質とメッシュ（色を変える前のもの、前の書き出しの写し）は、ファイルに残る。消すと番号がずれ、「既存の要素の番号を変えない」決まりに反する。増えるのは JSON だけである。

## 照合に足すもの・ゆるめるもの（`export/verify.rs`）
| いまの確かめ | 直し方 |
|---|---|
| 形状の配列に足した要素があるのに BIN を足していなければ失敗 | `accessors` と `bufferViews` だけに掛ける。`meshes` と `materials` は、BIN なしで増えてよい |
| 足した材質の `metallicFactor` が 0 | 足した材質は、次の3つのどれかでなければ失敗: ①元の材質のどれかと、`baseColorFactor` を除いて等しい、②材質なしの写し（`baseColorFactor` だけ）、③足した図形の材質（基本色と `metallicFactor: 0`） |
| ファイルにあるノードの、位置・名前・子のほかの項目が元と同じ | `mesh` が違ってよいのは、新しい番号が足したメッシュで、そのメッシュが元のメッシュと `primitives[*].material` を除いて等しいときだけ |
| 開き直したモデルの、名前・ワールド行列・三角形の数が文書と一致 | **描画ごとの基本色が、文書とビット単位で一致**を足す |
- 複製のノード（足したノード）は、写す元のノードと `mesh` が違ってよい。条件は上の3行目と同じである。

## 書き出しの結果の一覧（`app::session::export` が文にする）
- 「色を変えた部品 3 個: 材質 2 個とメッシュ 2 個を足しました。元の材質とメッシュは、ファイルに残しています」
- モデルにテクスチャか頂点の色があり、色を変えた部品があるとき: 「このモデルにはテクスチャ（頂点の色）があります。色を変えた部品は、ほかのソフトでは、選んだ色が掛け合わされて見えます」
- 新規の文書から書き出したとき: 「新規の文書を GLB として書き出しました」。以後は、このファイルが作業の対象になる（今の文のまま）。

## 要確認（使う前に確かめる）
- `inspect::open` と `container::parse` が、BIN もバッファも無い GLB（`empty_base()`）を受けること。受けなければ、土台用の入口で扱う。
- 色の書き方（`json::f32s`）で、`f32` → JSON → `f32` がビット単位で戻ること。戻らない値があれば、照合が落ちるので気づける。書き方を直す（戻らないまま、文書の色を読み直した値へそろえる逃げ道は作らない。次の書き出しのたびに写しが増える原因になる）。
- 材質の差し替えの拡張（プリミティブの `extensions` にある、見た目の切り替えの対応表）を持つファイル。写したメッシュにも対応表が写るので、ほかのソフトで切り替えると色が元へ戻る見込みである。試していない。`docs/glb.md` に「未確認」として書く。
- 写した材質は、名前が元と同じになる。同じ名前の材質が2つあるファイルを、ほかのソフトがどう扱うか（名前に連番を足す、1つにまとめる）は確かめていない。まとめられると色が戻る。進行役が1つのソフトで確かめ、だめなら名前の末尾に色の16進を足す。
