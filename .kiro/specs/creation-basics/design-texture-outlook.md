# 次の段階の見立て（テクスチャの表示と貼り付け）

設計ではない。次の段階の仕様を書く前に決めるべきことを並べた。ここに書いた数は、測った値ではなく計算である。

## 分かっていること
- いまの画面は基本色だけを描く。テクスチャ付きの GLB は、書き出すとテクスチャが残るが、画面では色だけになる（[brief.md](brief.md)）。
- 2048×2048 の画像1枚は、展開すると 16 MiB（RGBA 8ビット）、縮小版の列（ミップ）を足すと約 21 MiB。24枚で約 510 MiB になる。GPUのメモリがこの分だけ増える。
- 頂点の型は位置と法線だけで、UV を持たない。足した図形（立方体・球・円柱・平面）も UV を作っていない。
- ワークスペースの `image` クレートは、PNG の機能だけを有効にしている。`Cargo.lock` に JPEG の読み取りのクレートは載っているが、どの経路で入っているかは確かめていない。

## 決めるべきこと
- **画像の読み取り**: GLB の中の PNG と JPEG を読む。`image` の JPEG の機能を足すか（依存は増えるか、ライセンスは通るか）。WebP と圧縮テクスチャ（KTX2）は対象にするか。壊れた画像・巨大な画像（展開後の大きさの上限）をどう断るか。
- **GPUのメモリの上限と縮小**: 上限を決める（例: テクスチャ全体で 256 MiB）。超えるときは、長辺を半分ずつ縮めて収める。縮めたことを画面に出す。圧縮（BC・ASTC）は、装置ごとの対応と変換の時間が要るので、最初は使わない案が軽い。
- **読み込みの順**: 形状を先に見せ、画像は後から少しずつ送る（いまの「予算つきの転送」に乗せる）。画像を待たずに操作できること。
- **頂点の型**: UV を足すと、頂点が 24 → 32 バイトになる（全モデルの形状のメモリが3割増える）。UV を別のバッファにして、テクスチャのある形状だけ持つ案と比べる。
- **描画**: 基本色のテクスチャだけか、金属らしさ・粗さ・法線の絵まで描くか。色の空間（sRGB の画像をリニアで読む）。繰り返しと反転（サンプラー）。UV の変換の拡張。表示の切り替え（テクスチャを出さない軽い表示を残すか）。
- **`Draw` に足す情報**: 材質の番号、テクスチャの有無、金属らしさ・粗さ。組み立てている箇所が多いので、型の変更は1回で済ませる。この段階で、色の欄の注意（モデル単位）を部品単位にできる。
- **足した図形の UV**: 立方体は面ごと、球は経度と緯度、円柱は側面を巻く、平面はそのまま。寸法を変えたときに絵が伸びるか、繰り返すか。
- **画像ファイルから貼る操作**: ファイルを選ぶ、またはドロップする。貼る先は選んだ部品。取り消し、未書き出しの印、同じ画像を複数の部品で使い回すこと、貼った画像を外す操作。
- **書き出し**: 画像のバイト列を BIN に足し、`images`・`textures`・`samplers`・材質の写しを末尾に足す（色の写しと同じ「足すだけ」）。元の画像は残す。4GiB の上限。画像を変えていない部品の JSON は変えない。
- **公開物に利用者のパスを残さない**: 画像は GLB の中に埋め込み、外部ファイルの参照（`uri`）を書かない。画像の名前には、ファイル名（フォルダを含まない）だけを使うか、付けない。レビューJSON に画像の場所を書かない。画像に入っている撮影情報（EXIF など）を、そのまま埋め込むか落とすかを決める。
- **軽さの約束**: テクスチャを出す・出さないで、メモリと開く時間がどれだけ違うかを、実機で測ってから既定を決める。測る前に「軽い」と書かない。
