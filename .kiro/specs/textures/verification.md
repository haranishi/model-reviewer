# 検証の記録（画像の表示・貼り付け・書き出し。2026-11-28、macOS 27.2.1・Apple M4 Pro）

## 公開版 805dda5 の再現と修正

実装を変える前に、下表の14件で失敗を確認した。13件は新規、9番は既存試験の強化。

| 指摘 | 修正前の失敗と、修正後に確かめた挙動 | 試験名 |
|---|---|---|
| 1 | 複製は取り消しても焼いた材質を指し、図形と STL は2回目に UV が1組から2組に増えた。複製は開いた時点の形状・材質に戻り、図形と STL は大きさを3回変えても1組。 | `duplicate_undo_restores_external_reference`、`shape_reuses_box_set`、`stl_reuses_box_set` |
| 2 | 明示的に外しても外部画像の参照が復活した。外した出力では `baseColorTexture` を省き、履歴を貼る前まで戻した出力では元の画像を指す。 | `removal_clears_external_reference` |
| 3 | 自分の出力のレビューを復元すると、外した画像が GLB に残っても通知が消えた。復元後もハッシュを引き継ぎ、使用中は通知せず、最後の参照を外すと1枚と知らせる。出力に画像のバイト列が残ることも照合。 | `restored_review_tracks_pasted_hash` |
| 4 | ドロップ時は先頭の照会が画面上で完了し、時間切れ時は設定と同じ実体かをその場で調べていた。照会を止めた状態でも選択でき、最初の部品に貼れる。時間切れはパスだけを控え、同じ実体への設定保存を拒否する。 | `drop_header_waits_off_ui`、`timeout_defers_alias_check_until_save` |
| 5 | 同じ配列を指す32組が別々に書かれ、残り容量が足りなくても UV の展開が始まった。32組が同じアクセサを指し、全組が収まらない場合は展開前に断る。 | `baked_aliases_share_accessor`、`preflight_precedes_uv_read` |
| 6 | 未使用頂点で外形が広がる平面の複製は、2回目の出力で UV 照合に失敗した。焼く前の中心で照合し、2回の GLB がバイト単位で一致。 | `duplicate_keeps_projection_center` |
| 7 | 2番目の描画で法線用 UV を取り違えても照合を通った。元の組だけが違う場合、出力の組だけが違う場合の両方を検出する。 | `verify_checks_source_uv_refs`、`verify_checks_output_uv_refs` |
| 8 | 正常な GLB を残して次の書き出しを意図的に失敗させると、以前の縦横比試験は通った。毎回保存先を空け、今回の出力成功を確かめてから座標を読む。 | `aspect_test_detects_failed_export`（対象は `repaste_preserves_size_and_updates_aspect`） |
| 9 | 50 ms 後の判定が、読み取り前にも通った。試験用時計を期限まで進め、読み取りを再開し、結果の送信処理が終わった後で画像が増えていないことを確かめる。 | `hung_paste_times_out_and_unblocks_writes` |

読み込み試験の期待値は、表示できない基本色の画像も取り消しに備えて元材質を控える設計に合わせた。画像・UV が読み込まれず警告が出ることに加え、材質番号と表示できる描画との区別を検査する。ドロップの既存試験は判定の完了を待って同じ結果を検査する。

`cargo deny check advisories` は、依存の保守終了の知らせ（アクセシビリティ用の依存の下にある zvariant ほか）で、公開中の版でも失敗する。この変更では依存の版を変えていない。

## 実物のアプリでの確認
- 図形（立方体）と STL の箱に横長の画像を貼ると、部品の中央に縦横比を保って貼れた。書き出して開き直した立方体は同じ見た目だった。貼った画像と元の STL の中身は変わらなかった。
- 実寸の部品30個を材料ごとの11組にした机の見本（計算で作った画像）に、組ごとに画像を貼った。11枚すべてが表示され、「1枚の大きさ」は指定した値になり、書き出した GLB を開き直して同じ見た目だった。
- 書き出した GLB（机・立方体・STL の箱）を Blender 5.2.2 で開くと、画像の参照があり、アプリと同じ向きと並びで描かれた（机は画像11枚・メッシュ30個）。
- 箱形で貼る → 書き出し → 大きさを変えて書き出し → 別の画像で書き出し → 取り消し3回 → 書き出し、で元の形状と材質の参照に戻った（GLB の中身を照合）。
- 見本の GLB を開いてから別の装置へ移し、移した先への書き出しとレビュー保存を試すと、中身は変わらなかった。

## 軽さ（値と条件は [docs/measurements.md](../../../docs/measurements.md)）
- 初回表示は画像の有無で変わらなかった（16〜20 ms）。全部の画像が出るまでは、24枚×2048画素で203 ms、96枚×2048画素（1024へ縮小）で約1.0秒。
- 使用メモリ（GPU の分を含む）は、画像なしで約250 MiB、24枚×2048画素で808 MiB、`--texture-budget-mib 128` で403 MiB。
- 上限の既定 512 MiB は変えない。2048画素の画像24枚を縮めずに出せる大きさで、使用メモリを抑える起動の引数がある。256 MiB へ下げる案は残す。

## レビューと直し
- 別の担当が全体を2回読んだ。1回目は重大1件（貼る途中の書き出しで元の画像を上書きできる）と高5・中3・低2、2回目は高1件（書き出しを重ねてから取り消すと書き出しが失敗する）と中1・低5。重大と高はすべて直し、それぞれ試験を足した。
- 実機の確認で見つけて直した: 画像が面の中央で4つに割れ、横長の画像が正方形に伸びる／「1枚の大きさ」に打つと前の値の後ろに足される／前面でないウィンドウで打った値が消える／取り消した画像がファイルに残ることを知らせない。
- 公開した後に、別の系統がもう一度読んだ。高5・中2・低2を再現して直した（冒頭の表）。
- 直さず記録するもの: 読み込みの切り替え中は、圧縮した画像の写しが2つの読み込み分になる。閾値で描かない MASK の部品も、当たり判定に残る。
