# 当たり判定・注釈・レビューJSON

## 当たり判定（CPUで行う）
GPUで番号を描いて読み戻す方式は採らない。CPUで行えば、GPUの無い環境でも選択と注釈を試験でき、注釈に必要な「部品のローカル座標」もそのまま得られる（捨てた案は [design-decisions.md](design-decisions.md)）。

1. `ui::viewport` がクリック位置をNDCへ直し、`OrbitCamera::screen_ray` で光線を作る。
2. **部品で絞る**: 実際に表示されている（`Visibility::effective`）ノードのうち、`world_aabb` に光線が当たるものだけを候補にし、入り口の近い順に並べる。非表示の部品はここで外れるので、見えている部品より先に選ばれることはない（要件5.10）。
3. **三角形で絞る**: 候補ごとに、光線をその部品のローカル空間へ移し、プリミティブの索引（BVH）をたどる。すでに見つけた交点より遠い候補は調べない。
4. 最も近い交点を `Hit` として返す。`local_pos` と `local_normal`（三角形の幾何法線）を含む。

- **光線をローカルへ移すとき、方向を正規化し直さない。** 正規化すると距離 `t` の尺度が部品ごとに変わり、拡大率の違う部品の前後を取り違える。原点と方向を逆行列で移すだけにすれば、`t` はワールドでの値のまま比べられる。
- ワールド変換の逆行列が有限でない部品（拡大率0など）は対象から外す。
- 索引は**プリミティブごとに1つ**で、同じメッシュを使う部品の間で共有する。部品の数ではなく、形状の種類の数だけ作ればよい。
- 索引は自前の小さなBVH（中央値で分割、葉は三角形8個以下、たどるときは再帰しない）にし、`PickIndex` の内側に隠す。外部クレートへの差し替えは、公開の型を変えずにできる。差し替えを検討する目安は、1000万三角形のモデルで構築が数秒を超える、または1回の判定が1フレーム（16ms）を超えるとき。
- 部品の絞り込みは線形に全ノードを見る。10万ノードで1回あたり1ms未満の見込みで、クリックのときしか走らない。ノード側の階層的な索引は、実測で必要になってから足す。
- 注釈の印（ピン）は3Dの当たり判定より先に調べる。印は画面上の円なので、eguiの当たり判定で足りる。

## 注釈の位置の持ち方
- 注釈は「付いたノード」と「そのノードのローカル座標での位置・法線」を持つ（要件6.2）。画面の座標もワールド座標も保存しない。
- 表示するときは毎フレーム `node.world × local_pos` でワールド座標にし、`OrbitCamera::project` で画面に置く。カメラを動かしても、モデル上の同じ点を指し続ける。
- ローカル座標にした理由: 将来、部品を動かす機能が入っても、注釈は部品に付いて動く。ワールド座標で持つと、そのとき全注釈の変換が必要になる。
- 描かない条件は2つ。付いたノードが実際には非表示のとき（一覧には「非表示の部品」と出す）と、`project` が `None`（カメラの背面）のとき。画面の外にあるものは、切り取られるに任せる。
- **他の部品に隠れた注釈は「隠れている印」で描く。** 同じ見た目で手前に描くと、手前の別の部品に付いた印に見えたため（実機の採点で指摘）。目の位置から注釈の点へ `core::pick` で光線を1本撃ち、点までの距離より手前（距離の0.1%の余裕を引く）に面があれば隠れとみなす。点そのものの面は余裕で除く。隠れた印は中を塗らない破線の輪と薄い番号で、色に頼らず形で見分ける。見えている印を後から描いて上に重ねる。光線は1回の描画で注釈の数だけ。索引ができるまでは通常の印で描く。
- 番号は一覧の並び順（1から）で、3Dの印と一覧の両方に同じ番号を出す。`id` は内部の識別で、表示しない。

## レビューJSON v1
```json
{
  "format": "model-reviewer.review",
  "version": 1,
  "app_version": "0.1.0",
  "model": {
    "file_name": "review-sample.glb",
    "path": "/work/models/review-sample.glb",
    "relative_path": "../models/review-sample.glb",
    "size_bytes": 18244,
    "hash": { "algorithm": "blake3", "hex": "9f2c…（64桁）" },
    "node_count": 14
  },
  "hidden_nodes": [ { "gltf_index": 6, "name": "wheel_FL" } ],
  "annotations": [
    { "id": 1, "node": { "gltf_index": 9, "name": "arm_tip" },
      "local_position": [0.12, 0.4, -0.05], "local_normal": [0.0, 1.0, 0.0], "text": "ここの角を丸めたい" }
  ],
  "views": [
    { "id": 2, "name": "正面",
      "camera": { "projection": "perspective", "target": [0.0, 0.5, 0.0],
                  "yaw_deg": 0.0, "pitch_deg": 10.0, "distance": 4.2, "fov_y_deg": 40.0 } }
  ]
}
```
- `hidden_nodes` は、利用者が**自分で非表示にした**ノードだけを書く。親に連れて非表示になった子は書かない。復元したとき、親を表示へ戻せば子も元どおりになる。
- ノードは `gltf_index`（GLB内のノード番号）で指す。本アプリ内部の並び順には依存させない。`name` は人が読むためと、取り違えの検査のために添える。
- 角度は度、座標と距離はモデルの単位。数値はすべて有限でなければならない。保存の文字列化の前にも有限値とカメラ値の範囲を検査し、失敗時はエラーを返して前のファイルをそのまま残す。
- 注釈と視点の `id` は全体で一つの連番とし、重複する `id` や `u64::MAX` 近くの `id` を持つJSONは `parse` で拒む。新規採番は既存と重複しない値だけを返す。
- `path` は保存時の絶対パス、`relative_path` はJSONから見た相対パス。モデルとJSONを同じフォルダごと動かしても見つかるように両方を書く。**絶対パスにはユーザー名が含まれることがある**ので、README に「共有する前に確かめる」と書く。
- 読むとき、知らない項目は無視する。`version` が本アプリの対応より大きければ読まない（要件8.7）。`format` が違えば、レビューJSONではないと伝える。
- 項目を足すだけの変更では版を上げない。意味が変わる、または項目を消すときだけ上げる。古い版を読む変換は、版を上げるときに用意する。
- 書き出しは、同じフォルダの一時ファイルへ書いてから名前を付け替える。書いている途中で落ちても、前のファイルを壊さない。
- 日時は入れない。同じ状態からは同じ内容のファイルができ、差分が読みやすい。

## モデルの識別と、合わないときの方針
- 識別は**ファイル全体の blake3 ハッシュとバイト数**。読み込みのときにどのみち全体を読むので、追加の読み取りは無い。更新日時やファイル名は、内容が同じでも変わるので識別に使わない。
- レビューJSONを開いたときの流れ:
  1. いま開いているモデルの識別が一致すれば、そのまま復元する。
  2. 一致しなければ、`relative_path` → `path` の順にファイルを探して別スレッドで識別を比べる。先の候補が違う内容でも次の候補を確かめ、一致する候補があればそれで復元する。どの候補も一致しないときに不一致を出す。
  3. **見つからない**: 探した場所を示し、「モデルを指定…」でGLBを選ばせる（要件8.5）。
  4. **内容が違う**: 何も復元しない。保存時と今の大きさ・ハッシュの先頭を並べて見せ、「別のGLBを指定」か「やめる」を選ばせる（要件8.4）。
- **強制的に当てはめる選択肢は置かない。** 形が変わったモデルへ注釈を移すと、利用者が気づかないまま誤った場所を指す。位置を見ながら付け直す支援は、後続の範囲とする。
- 識別が一致しても、`gltf_index` がモデルに無い、名前が違う、といった矛盾があれば `UnknownNode` として復元を止める。JSONが手で書き換えられた場合の備えである。
- 指定し直したモデルで復元した後は、次の保存で新しいパスを書く。
- 未保存の変更（表示切り替え・注釈・視点の追加や変更）に加えて、注釈の下書き欄に未登録の文字がある状態と注釈本文を編集中で未確定な状態も `Session` が未保存として扱い、失う操作の前に確認する（要件8.8）。カメラを動かしただけ、選択を変えただけでは未保存にしない。
