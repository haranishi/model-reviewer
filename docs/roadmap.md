# ロードマップ

model-reviewer は、軽くて速い3D制作ソフトを目指す道の途中にある。初版は「見て、指して、残す」だけのレビューツールだった。次の段階（操作画面と編集の土台）で、その上に「動かして、渡す」を足した。この文書は、これまでの構成が後の何を可能にしているかと、やらないと決めたことを書く。時期は約束しない。順番と、進む条件だけを示す。

## 進め方の原則
- **測ってから速くする。** 性能の話は、アプリの詳細パネルと `--log-metrics` が出す値で行う。他のソフトとの比較は、同じモデル・同じ機械・同じ条件で測ったときだけ書く。
- **小さく足す。** 1つの変更は1つの目的に絞る。新しい機能は、いまある境界（クレートの依存の向き）の中に収まる形で提案する。収まらないなら、先に境界の変更を議論する。
- **コアは画面にもGPUにも依存させない。** `model-reviewer-core` に wgpu・egui・ファイル形式のクレートを入れない。これが崩れると、テストと再利用の土台が無くなる。
- **利用者のファイルを守る。** 元のモデルは書き換えない。書き出すときは別のファイルにする。ネットワークへは送らない。

## 初版の構成が可能にしていること
| 初版で決めたこと | 後で効く場面 |
|---|---|
| 形状・カメラ・当たり判定・レビュー状態を、GPUと画面に依存しないコアに置いた | 形状編集や計測の処理を、画面なしでテストしながら足せる。コマンドラインの道具や別の画面からも同じ処理を使える |
| 状態の変更を `Command` の1か所に絞った | 取り消し／やり直し、操作の記録と再生、キー割り当ての変更を、入口を増やさずに足せる |
| 読み込みを「バイト列 → `Model`」の関数にし、形式ごとのクレートに分けた | OBJ・STL・STEP などを、同じ形のクレートとして足せる。コアは変わらない |
| 注釈を「部品とローカル座標」で持った | 部品を動かす機能が入っても、注釈は部品に付いて動く |
| レビューJSONに形式名と版を入れ、知らない項目は無視して読む | 項目を足しても古いファイルが読める。古いアプリが新しいファイルを誤読しない |
| カメラの保存形式に `projection` を入れた | 平行投影を足しても形式を作り直さない |
| 描画をeguiから切り離し、画像へ描く作りにした | 複数のビュー、サムネイルの生成、画面なしの描画テストに使い回せる |
| 当たり判定の索引を1つの型の内側に隠した | 実測で遅ければ、公開の型を変えずに中身を差し替えられる |
| 自動操作と画面なしのテストを最初から用意した | 貢献者が、自分の変更で一連の操作が壊れていないことを手元で確かめられる |

## 済んだ段階：操作画面と編集の土台
下の「使い切る」「大きなモデル」の段階より先に、制作ソフトらしい画面と編集の土台を入れた。設計寄りと造形寄りのどちらへ進むにも要る部分だからである。設計と検証の記録は `.kiro/specs/editor-foundation/` にある。次の4つの区切りで作った。
1. **見る**: 床の格子と軸、向きを切り替える立方体、透視と平行の切り替え、面・面と線・線・透かしの表示
2. **動かして渡す**: 移動・回転・拡大（ハンドルと数値入力）、取り消しとやり直し、GLBの書き出し
3. **足す・消す**: 立方体・球・円柱・平面の追加、複製、削除
4. **測る**: 2点の距離、単位の表示

この段階で決めたことのうち、後に効くもの:
| 決めたこと | 後で効く場面 |
|---|---|
| 形状は不変のまま共有し、部品の表だけを書き換える文書を上に載せた | メッシュの編集を足すとき、変えた形状だけを差し替えればよい。変えていない形状は送り直さない |
| 部品を読む口を1つ（`SceneRead`）にした | 文書の持ち方を変えても、当たり判定・表示・保存のコードは変わらない |
| 取り消しを「逆の操作」で持ち、未保存の印が付く操作すべてを対象にした | 新しい編集を足すときは、逆の操作を1つ書けば履歴に入る |
| 書き出しは、元のGLBの中身を保ち、変えた所だけを直し、既存の番号を変えない | 表示に使っていないデータ（テクスチャ、アニメーション、知らない拡張）を失わない。対応する表現が増えても方式は同じ |
| ハンドルと立方体を、3Dの描画ではなく画面の部品として描いた | 新しい道具を、GPUなしの試験つきで足せる |

この段階でやらないこと（後で足せる形にしてある）: 頂点・辺・面の編集、スケッチと拘束、親子関係の付け替え、複数選択、色と材質の編集、角度の計測、吸着、空からの新規作成、自動保存、削除した部品のデータを取り除く書き出し、別の作業で書き出したGLBへのレビューの引っ越し。

## 済んだ段階：寸法を確かめる（CAD寄り）
角や辺に吸着する計測、断面の表示、表示の単位（mm・cm・m）、STL の読み込みと GLB への書き出し（[stl.md](stl.md)）、寸法を指定した図形と選んだ部品の外形を入れ、確認まで済んだ（記録は `.kiro/specs/cad-inspect/verification.md`）。残る課題は、STL の上の向き（Z が上のファイルは寝て見える）を選べるようにすることと、部品が非常に多いときの吸着の探索を速くすることである。設計は `.kiro/specs/cad-inspect/` にある。

## これからの段階
### レビューツールとして使い切れるものにする
実際のモデルで使い、出た不満を直す。
- 部品の名前での絞り込み、複数選択、選択以外を隠す
- 注釈へ視点を合わせる、視点の切り替えの補間
- 角度の計測
- テクスチャと頂点色、半透明の表示
- 量子化された頂点形式（`KHR_mesh_quantization`）、拡張によるインスタンス配置
- 明るい配色、パネル幅やウィンドウ位置の記憶、英語の表示
- Windows と Linux の画面の確認（ビルドと自動テストは CI で通る。画面を動かして確かめたのは macOS のApple Siliconだけ）

### 大きなモデルを軽く扱う
集めた実測値をもとに、遅い場所から直す。対象は、数千万三角形・数十万部品のモデル。
- 視野の外の部品を描かない、遠くの小さな部品を省く
- ノード側の階層的な索引（当たり判定と可視判定の両方に使う）
- ファイルの読み方の見直し（メモリマップ、段階的な表示）
- GPUの処理時間の計測（タイムスタンプ問い合わせ）と、メモリ使用量の内訳
- 圧縮形式（Draco、meshopt）の読み込み

### 編集を広げる
土台の上に足すもの。どちらの方向（設計寄り／造形寄り）を先にするかは、土台ができてから決める。
- 親子関係の付け替え、複数選択での変形、吸着、ハンドルの向きの切り替え（ワールド／部品）
- 色と材質の編集、形の稜線だけを描く表示
- 空の状態からの新規作成（第5段階「作るための基本」で入れた。設計は `.kiro/specs/creation-basics/`）、自動保存と復旧
- 不要なデータを取り除く書き出し、書き出したGLBへのレビューの引っ越し

### 制作ソフトへ
メッシュの編集、精密な形状の表現（境界表現、拘束つきのスケッチ）など。どれも大きな設計判断を伴うので、着手の前に設計の文書を作り、公開の場で議論する。既存のCADカーネルやメッシュ処理のクレートを使うか、自前で持つかも、そのとき決める。

## 初版でやらないと決めたこと
| やらないこと | 理由 |
|---|---|
| プラグインや拡張の仕組み | 何を差し替えたいかが分かる前に境界を固定すると、後で身動きが取れなくなる |
| 独自の汎用エンジンやCADカーネル | 初版の機能に要らない。必要な描画と当たり判定だけを書く |
| 取り消し／やり直し | レビューの操作は少なく、やり直しが軽い。入口は用意してあった（編集の土台の段階で入れた） |
| アニメーションの再生、物理、写実的な描画 | 静的なモデルの確認が目的 |
| クラウド共有、ログイン、課金 | 手元で完結する道具にする。共有はJSONファイルの受け渡しで足りる |
| モデルが変わった後の注釈の自動引っ越し | 誤った場所を指す注釈を、気づかれないまま作ってしまう |
| フォントや外部の素材をリポジトリに置くこと | 権利の確認を要らなくする。実行ファイルには egui の既定の欧文・絵文字フォントが組み込まれる |
| 速さの宣伝 | 測っていない比較は書かない |

## 参加するには
- 使い方と検証の手順は README、貢献の条件は CONTRIBUTING にある。ライセンスは MIT OR Apache-2.0 で、提出されたものは同じ条件で提供されたものとして扱う。
- 設計の背景は `.kiro/specs/model-reviewer/`（初版）と `.kiro/specs/editor-foundation/`（編集の土台）にある。判断の理由と、検討して捨てた案を書いてあるので、提案の前に読んでほしい。
- 上の段階に無い提案も歓迎する。その場合は、どの利用者の何を解くのかと、どの境界に収まるのかを添えてほしい。
